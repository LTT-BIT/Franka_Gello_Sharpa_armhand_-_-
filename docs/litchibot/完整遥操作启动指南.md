## 二、normal hardware full teleop（日常路径，独立于 supervised）

### 一次性设备绑定

先创建部署配置；已有文件时不要覆盖：

```bash
cd /home/user/gello_upper_body_teleop
cp -n config/litchibot/hand_devices.example.json config/litchibot/hand_devices.json
nano config/litchibot/hand_devices.json
```

填写实际设备序列号：

```json
{
  "serials": {
    "left": "实际左手设备序列号",
    "right": "实际右手设备序列号"
  }
}
```

左右必须不同，不能原样保留上面的中文占位文字。程序启动时会核验实际 SDK 的 serial 和 hand side。这是一次性部署绑定，不是每次 Start hand 的验收 permit。

### 日常启动

LitchiBot：

```bash
cd /home/user/gello_upper_body_teleop
./ops/run/run_gello_full_teleop.sh \
  --hand-source litchibot \
  --profile LYG226360006 \
  --hardware
```

Manus：

```bash
cd /home/user/gello_upper_body_teleop
./ops/run/run_gello_full_teleop.sh --hand-source manus --hardware
```

日常模式连接实体设备，启动后双臂、双手授权仍关闭。GUI Start hand 授权对应侧；Stop hand / DISENGAGE ALL 撤权。日常模式不要求验收 permit，也不要求按住 F12。

每一帧仍经过 RawContinuityGate、22D/joint order、NaN/Inf、joint limits、freshness、watchdog、timeout、discontinuity 和 FAULT latch 检查。LitchiBot normal/full fake 单帧 moderate/快速动作只 WARNING，合法 target 原值发送，不再使用自加 0.5 rad/s shared slew clamp。partial-valid 使用原 vendor fallback，临时数据/control 问题 PAUSED 并可自动恢复，不再使用 validation/pattern latch。极端跳变和基础危险错误仍 HARD_FAULT；supervised 保留严格行为。Start hand 不能覆盖安全门。规则与逐 joint 统计见 [normal discontinuity 分级与恢复](normal_discontinuity.md)。

不加 `--hardware` 或验收模式参数时，默认是 fake/no-send。`--dry-run`、`--hardware`、`--supervised-hardware-validation` 互斥。

## 五、LitchiBot 软件 dry-run

终端 A 执行：

```bash
cd /home/user/gello_upper_body_teleop
./ops/run/run_gello_full_teleop.sh \
  --hand-source litchibot \
  --profile LYG226360006 \
  --dry-run
```

此入口同时启动原 arm 子系统、手部子系统和 Operator GUI。LitchiBot 读取真实手套；Sharpa 使用 fake driver，实体 Sharpa 发送为 0。

**`--dry-run` 只指定 Sharpa no-send，不是整个机器人系统的仿真开关。** arm 子系统仍使用原生产启动流程。本轮验证手部时，不点击 `Start arm` 或 `Hold arm`，FR3 保持未授权。

GUI 操作：

1. 启动后，左右 arm、hand 的运动授权默认关闭。
2. normal/full fake 显示 READY 后，可独立 Start 左右手；不要求 30 帧 warmup 或验证仪式。后台 glove/V3.5/retarget/driver 持续运行。
3. 点击 `Left Start hand`，只授权左侧 fake Sharpa 跟随；右侧同理。
4. 动作使用“自然伸展 → 缓慢半握拳 → 自然伸展”。
5. 点击对应侧 `Stop hand` 只关闭该侧 forwarding；后台手套读取、解算、retarget、driver、device connection、state、tactile 继续运行。
6. `DISENGAGE ALL` 同时撤销双臂和双手授权。

这里实体 Sharpa 不会动，这是 dry-run 的预期行为。GUI 显示 ACTIVE 表示 supervisor 授权生效，不表示实体手正在运动。

若显示 PAUSED，该侧或控制链临时暂停，pipeline/device connection 持续运行；Start hand permit 保留，输入/控制恢复后自动 ACTIVE，无需稳定帧仪式；暂停期间仍可 Stop hand。若显示 HARD_FAULT（旧策略 FAULT），读取 Event log 原因并处理故障；GUI Start 或重连不能清除硬故障。full 模式的 Open hand 暂未启用，点击会明确拒绝，不发送猜测的开手姿态。

## 七、首次实体验收：supervised validation

此阶段由现场具备机器人操作资格的成年人按设备 SOP 执行。它会连接实体 Sharpa；当前软件通过不等于已经通过实体验收。

验收 permit 的模板是：

```text
config/litchibot/validation_permit.example.json
```

模板中的 false、空值和零时间不能授权实体运动。现场人员需根据真实情况填写操作人、SOP、急停/工作区/已知风险确认、实际左右设备 serial、profile、有效期及新会话 token，并将实际 permit 文件权限设为 0600。不能直接把模板当作有效 permit 使用。

假设实际 permit 保存为 `config/litchibot/validation_permit.json`，full 验收命令为：

```bash
cd /home/user/gello_upper_body_teleop
./ops/run/run_gello_full_teleop.sh \
  --hand-source litchibot \
  --profile LYG226360006 \
  --supervised-hardware-validation \
  --validation-permit "$PWD/config/litchibot/validation_permit.json"
```

full 验收中，GUI Start hand 请求该侧许可，F12 是额外 hold-to-run 条件。松开 F12、失焦、失联或任何安全异常都会锁停。保留原验收位移窗口、运行时间窗口和运行时检查。此阶段仍不测试 FR3 运动。

如果只验收 hands，可继续用原独立入口：

```bash
./ops/run/run_sharpa_hands_cyclonedds.sh \
  --hand-source litchibot \
  --supervised-hardware-validation \
  --validation-permit "$PWD/config/litchibot/validation_permit.json"
```

独立入口继续使用原验收 supervisor 的 hold-to-run 面板。上述两个验收入口只能选择一个运行。
