## 结论与证据边界

历史最大跳变是左小指 `pinky_MCP_FE`（0-based 18，第 19 关节），`1.5708 → 0.0`，signed delta `-1.5708` rad。它在 SDK/V3.5 的 canonical joint 输出中就已出现：`pinky_mcp_flex = 2.094395160675049 → 0` rad；SDK kinematic pose 中为 `1.65 → 0` rad，同时小指 swing `+0.6 → -0.6`。这两个通道的 validity 均保持 true。

目前能证明的是“异常已在 SDK 输出边界存在，接入层未创造它”；硬件 / 校准 / SDK 算法三者的责任尚未最终区分。

## 2. 为什么恰好是 1.5708

`config/litchibot/wave.json` 左侧 `pinky_MCP_FE`：唯一 source 为 `pinky_mcp_flex: 1.0`，input range 是 `[0,75]` degrees，output range 是 `[0,1.5708]` rad，`clamp_inputs=true`，此规则没有 offset、fixed_value 或额外 scale。

```text
q = 1.5708 × clamp(degrees(pinky_mcp_flex) / 75, 0, 1)
之前：1.65 rad = 94.538036° → normalized 1.260507 → 厂家 input clamp 到 1 → q=1.5708
之后：0 rad = 0°         → normalized 0        → q=0
```

所以确实涉及固定 π/2 近似边界：**跳变前已在映射上界，跳变后从上界直接落到零**。不是异常帧被接入层突然写入 π/2。

`sharpa_schema.json` 该 joint 限位 `[-0.17453293,1.5708]`，但这两个值本来就在范围内，外层 `np.clip` 都没有改变数值。旧日志 `clipped_joints=[]` 只表示外层 schema clipping，不能据此说厂家内部 clamp 没发生；新诊断明确分别记录二者。

扫描范围与命中见 `code_search.txt`，覆盖 wave、CMC mapping、schema、SDK pose 处理、厂家 clamp、invalid/hold/fallback/initial/offset。`dexterous_hand_cmc_mapping.json` 是拇指转换，没有小指 MCP 输入规则。厂家 CMC stabilization 仍关闭，没有改变。

候选上游原因包括 finger decomposition 的分支/符号变化、校准姿态不匹配、或异常传感器输入导致角度落在两个边界；`120°→0` 和 `+0.6→-0.6` 的组合提示这种可能性，但现有历史证据不足以选择其中一个。没有把候选原因写成已证明的结论。

## 6. 变更、复核与最小修复建议

本轮只改 `backend.py` / `retarget.py` 以增加 **LITCHIBOT_DIAGNOSTICS_FILE 开启时** 的观察日志；环境变量未设时关闭诊断。mapper 新增的 diagnostic 参数默认 false，原输出逻辑保持；日志仅计算 normalization 等观察值。没有改 vendor 函数、mapping JSON、SDK 或生产启动图。

新增 `diagnostics.py`、`analyze_discontinuity.py`、`analyze_diagnostic_layers.py` 和专项测试。分别用于记录、离线统计、精确 raw/solved 关联。JSON/CSV 含完整 22 joint、事件上下文与层间证据；大体积 raw/solved 文件保留在 `/home/user/litchibot_glove/validation/logs/discontinuity_controlled_{left,right}`，没有加入工程文档目录。

测试：原 Python 3.10 的 backend / hand pipeline / 架构及专项回归共 50 passed、8 skipped（ROS 专项在 ROS 环境另跑）；ROS Terminal 2 + diagnostic 16 passed。诊断开/关输出数值及 validity/hold 完全一致；厂家函数原样校验通过。Terminal 2 既有静态回归、fake SDK loader 阻断和 57 个受保护文件 hash 验证通过。

**尚未实施任何修复。** 首选最小根本修复应在实际产生异常的上游：以 raw+solver_diagnostics 的复现包向厂家确认小指 root flex / swing 分解、校准与 validity 规则。若最终证实是分解分支，修该分支连续性及异常 validity，不改 Sharpa 映射、限位或 Terminal 2 架构。若是输入/校准不匹配，则按本人姿态重新校准并核验传感器位置。

作为独立防护的候选，接入层可显式检测“valid=true 但突变”的 joint，将其标为异常、保持上一已验证值并报告/要求重新采集；它应透明记录而非静默置零或低通。阈值和恢复条件必须根据真实动作数据验证，此轮未添加。这样的保护可以降低风险，但本身不能证明 SDK 根因已解决。
