## 1. 旧链路审计：实际存在两条路径

### A. 当前实际 Manus → Sharpa（保持原样）

```text
ops/run/run_sharpa_hands_cyclonedds.sh
  → portable_deps/litchi_hardware/pixi.toml 的 ros2 teleop task
  → ros2/src/manus_sharpa_teleop/manus_sharpa_teleop/launch/teleop.launch.py
  → manus_driver.node.ManusDriverNode.__init__
  → ManusNativeTracker.connect / read_frame
  → Native Manus bridge / 左右 HandSide / 25 点 HandTrackingFrame
  → manus_driver.node.frame_to_pose_array
  → /manus/left/keypoints、/manus/right/keypoints（PoseArray）
  → manus_sharpa_teleop.retarget_node.RetargetNode._on_keypoints
  → pose_array_to_frame（按左右订阅回调区分侧）
  → SharpaV4Retargeter.retarget（默认 v4；另有 analytic）
  → V4 worker 求解并返回 action.features[joint_names/joint_position]
  → /sharpa/left/command、/sharpa/right/command（sensor_msgs/JointState）
  → sharpa_driver.node.SharpaDriverNode._on_command
  → normalize_command（处理具名数组/左右前缀）
  → SharpaSdkHand.send_action → _write_joint_position
  → Sharpa Wave SDK set_joint_position
```

上述 ROS 源文件位于 `portable_deps/litchi_hardware/ros2/src/`；HAL 位于其 `src/litchi_hardware/`。
ManusNativeTracker 在 `hardware/manus/native_driver.py`；原生桥在 `hardware/manus/_native/litchi_manus_bridge.cpp`。
Sharpa HAL 在 `hardware/sharpa/sdk_driver.py`；22 关节和 rad 限位在 `hardware/sharpa/schema.py`。
原标定位于 `portable_deps/litchi_hardware/calibration/metaglove`，旧 launcher 仍使用它。
旧 retarget 有源时效检查；V4 filter alpha / analytic smoothing 是各自参数，不与 LitchiBot 混用。

GELLO → FR3 是另一进程，由 `ops/run/run_gello_arms_only.sh` 启动；本轮不改它，也不启动另一个 FCI 客户端。

## 2. 原厂 LitchiBot GUI 调用链

源码根：`/home/user/litchibot_glove/litchibot_glove_gui/src/teleop_gloves/`。

```text
main.py → sdk_loader.load_sdk（按 --sdk-path 选择原生 SDK）
  → 用户选择 / sdk_configuration.profile_id_for_user
  → sdk_bridge.SdkHandImuSolver（Profile、Pipeline、V3.5）
  → IMU manager / raw → SdkHandImuSolver._raw_frame
  → Pipeline 解算 → HandPose
  → SdkHandImuSolver._state（SDK kinematic 输出 + 完整 CMC 四元数）
  → HandPoseFrame.visualization_joint_values
  → retargeting.hand_pose_runtime.HandPoseRetargetRuntime.process_pose_frames
  → SharpaVisualRetargeter.map_hand_frame（父类 VisualAngleRetargeter）
  → DexterousCMCConverter.convert（完整 CMC 姿态投影到机器人专用轴）
  → VisualAngleRetargeter.map_visual_joints / _map_one_joint
  → SharpaVisualTarget：22 个具名 SDK rad 绝对关节目标
  → LitchiHandWorkbenchPage._apply_retarget_target
  → HandControlPanel.apply_pose / _send_current_pose
  → SharpaAdapter.send_pose → SDK set_joint_position
```

核心数据：每侧 11 IMU；SDK 标准姿态为 20 个关节/20 节点；raw 四元数 wxyz，解算四元数 xyzw；角度 rad，骨架位置 m。
`kinematic_hand_pose` 与 `unity_hand_pose` 不可混用。CMC 不直接用显示 yaw/swing，而用 `thumb_cmc_orientation_palm_xyzw` 的完整四元数。
GUI 原模型输出也会按 Sharpa spec 限幅。原 SDK 有其内置滤波；CMC mapping 的可选 stabilization 默认关闭；VisualAngleRetargeter 本身没有额外 EMA。

目前用户 `LYG226360006` 没有单独的 Wave retarget override，使用默认 `wave.json`。已比较正在使用的打包 GUI 与源码 GUI：Wave 和 CMC 两份 JSON 内容一致（文件换行格式不同）。

## 3. 新链路与汇合点

```text
--hand-source litchibot
  → adapters.litchibot.backend.LitchiBotHandPipeline
  → GloveSession.from_profile(LYG226360006, solver=v3.5, side=both)
  → subscribe_solved → _on_solved（按 HandPose.side 缓存）
  → tick（HandWorker 外线程；时效、序号检查）
  → SharpaRetargeter.map
      SDK kinematic_hand_pose + valid mask
      → 原厂 DexterousCMCConverter.convert
      → 原厂 VisualAngleRetargeter.map_visual_joints
      → 限位 + 无效依赖保留/标记
  → 统一具名 22 关节 rad target
      ├─ dry-run：JSONL / 终端统计；无发送器、无 UDP 命令、无 ROS publisher
      └─ 未来明确允许输出且每侧 engage：UdpSharpaSender.send
          → localhost UDP 5572
          → 新 ros_relay → TargetGate
          → /sharpa/<side>/command
          → 现有 SharpaDriverNode / SharpaSdkHand（复用旧硬件发送端）
```

最小汇合点是 **各自 retarget 之后的具名 22 关节目标/既有 Sharpa ROS command topic**。Manus 25 点和 LitchiBot 20 点不强行转换为同一种骨架，不复用 Manus 的标定或阈值。
统一 operator 新分支使用既有 HandWorker 生命周期和每侧 engagement；arm 代码未改变。

## 4. 有效性、时效和输出隔离

- 保留 source_id、sequence、source_raw_sequence、source_received_monotonic_ns、source_device_timestamp_ns、solved_monotonic_ns；本次设备时间戳为空时照样保留 null，不伪造设备时间。
- 标记每个 glove joint / Sharpa target 的有效性。无效依赖对应的 target 保留上次有效值；尚未有效过时用原厂 initial_values，并记录 `initial_fallback_joints`。
- 测试版左拇指不阻塞其他关节。实时输出 relay 对无效 target 使用之前的命令/首次新鲜反馈保持，不让 startup fallback 直接驱动实体关节。
- 数据超过 0.25 秒后停止发送，错误留在 side status；一个侧异常不影响另一个侧，不抛异常到 arm loop。
- 不自动重连停止的 SDK session；断流后保持状态，恢复连接需要重启入口。部分无效姿态可以持续出 target。
- 重复解算帧不重复处理。SDK 解算默认 30 Hz；最大设置 60 Hz。
- `dry_run=True` 时连 sender factory 都不会调用。统一 CLI `--dry-run` 在 arm/server/hardware 构造前返回到 hands-only 路径。
- 实体模式需 `--enable-hand-output` + operator 每侧 engage；发送器只向专用 localhost relay 端口发 named targets。
- relay 还需显式 `--enable-output`；检查来源格式、侧、序号、22 关节顺序、rad 限位、源时效、新鲜 Sharpa feedback、2 rad/s slew。
- 复用旧 driver 的新 launch 将 command timeout 显式设为 0.25 秒；超时 stop 后必须重新确认/连接恢复，不假设自动重新使能。
- 原 driver/HAL 本身 connect 会使能；因此新的硬件 bringup 脚本必须显式 `--enable-output` 才运行。没有把“发现成功”当成启动运动。
- `request_open`/手部 Home 等额外动作没有为 Sharpa 伪造姿态，目前明确不支持。只新增 glove-follow target 通道。
